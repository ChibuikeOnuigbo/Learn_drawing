# Character rigging and acting

Use when joints, weight, contact or props must stay coherent. The toolkit has two distinct rig systems; do not describe one as the other.

## A. 2D hierarchical cut-out

Native scene groups inherit transforms and visibility. An SVG asset can contain nested pivot groups for body, head and limbs. The working example is `examples/01-2d-moonlight/character.svg`, generated by `src/animation_mcp/character.py`.

1. Draw a neutral pose with clear joint centers and consistent proportions.
2. Establish parent chains: root → torso → head; torso → upper arm → forearm → hand; root → thigh → shin → foot.
3. Overlap joint artwork enough to hide gaps through the pose range.
4. Key storytelling poses before secondary motion.
5. Check eyes/props remain attached and limb lengths read consistently.
6. Rasterize actual pose variants when using an image sequence; name frames `%04d` from zero.

This is cut-out animation, not automatic mesh skinning or automatic drawing. A flattened PNG cannot acquire articulated limbs through a transform track.

## B. 3D weighted humanoid

The bundled rig has 15 bones, weighted geometry and four two-bone IK chains. Supported actions are `idle`, `wave`, `walk`, `pickup`, `reach`. It is a stylized procedural preset, not universal auto-rigging.

```json
{
  "name":"Performer","action":"wave",
  "position":[0,0,0],"color":[0.1,0.55,0.62],
  "target_keys":[]
}
```

Controls are `hand.R`, `hand.L`, `foot.R`, `foot.L`. Target keys specify a frame, control and local location. A supplied control track replaces that control's procedural action path; other controls continue their preset motion. Plan coordinated tracks rather than overriding one limb and expecting the whole performance to adapt.

## Coordinate and contact rules

- Rig position sets its origin. Target locations are local offsets added to that origin.
- Z is up; the preset floor is world Z=0.
- Neutral hand targets are approximately `(±0.75, 0, 1.0)`; feet `(±0.19, 0, 0.14)`.
- Keep targets inside the limbs' reachable envelope. A visually desirable world point can still be unreachable.
- If the root translates, planted world feet require local targets that compensate. In the reach preset, foot targets translate with the root in local coordinates so the world controls travel correctly.
- Do not copy local targets between actions without checking the root and pose phase.

The hard reach regression previously failed with IK error about 0.297 because targets were outside the envelope and feet did not account for root travel. The corrected preset measures about 0.000075. Preserve that correction.

## Blocking a reach/grasp

1. Establish the payload, pedestal and final hand pose.
2. Block anticipation → approach → contact/grasp → lift → settle.
3. Check hand-to-prop offset at the actual grasp frame.
4. Keep the prop fixed before grasp and attached to the evaluated hand afterward.
5. Audit every rendered frame, not just a attractive still.

The bundled pickup/reach actions create their own payload and pedestal. The grasp frame is action-specific; read the saved scene/rig metadata rather than assuming an arbitrary frame.

## Measured QA

`rig-qa.json` includes bone count, weighted vertices, armature modifier, IK-chain count, minimum evaluated foot-vertex Z, maximum IK target error, maximum payload hold error and a frame trace.

Current geometry gate:

- Minimum foot vertex Z ≥ −0.025 scene units.
- Maximum payload hold error < 0.001 after grasp.
- Maximum IK target error < 0.03.

These are preset geometry tolerances, not perceptual quality scores. A pass can still hide unattractive arcs, stiff acting or poor silhouette. A failure must be fixed in the pose/rig, not by deleting the check.

## Tools and proof route

Start with `render_3d_exercise(level="simple")` for a wave or inspect `examples/03-3d-hard/scene3d.json` for reach. Customize supported rig fields and use `render_3d_scene`. Preserve the `.blend`, scene JSON, video, `rig-qa.json` and inspection frames.

For arbitrary characters, topology-dependent weights, facial rigs, cloth or creature locomotion, use an external rigging workflow with appropriate assets. The MCP does not accept a custom armature specification or executable rigging code.

Accept only after checking contact and motion over time. Record the exact defect, correction and artifact path in the review report.
